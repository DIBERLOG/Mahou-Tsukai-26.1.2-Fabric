# Проверка изменений DeepSeek 0.32

Проверено 19 октября 2026 года. **Изменения существуют и основные наборы проходят, но сборка не готова к заявлению «всё работает». Дополнительные проверки обнаружили ошибки, которых нет в исходном чек-листе.**

Проверяемый JAR: `1.36.36-fabric.0.32-incomplete`, 7 569 746 байт.
SHA-256: `5b69c699ea537dc306fd0d1e697dd237b71d47b4c292eb19736e3828dfdc565b`.
Это последний хеш из присланного отчёта. Он подтверждён свежей сборкой и совпадает с копией в `artifacts/releases/v1.36.36-fabric.0.32/`.

Производственные исходники и баланс во время этой проверки не исправлялись. Добавлены только дополнительные серверные пробы в тестовый source set и этот отчёт с доказательствами. Изменения DeepSeek не коммитились и не публиковались проверяющим.

## Обнаруженные ошибки, по важности

### P1. Реальный сервер остановлен watchdog в пути движения William

В конце клиентского прогона, в 20:45:53 по журналу, сервер сообщил: `A single server tick took 60.01 seconds` и был принудительно остановлен. Верх стека: `BlockCollisions.computeNext → Entity.collectColliders → Entity.collide → WilliamEntity.move:185 → WilliamEntity.tick:175`.

Это **реально наблюдавшееся падение**, а не предположение по исходникам. Короткий стек сохранён в `audit-0.32/william-watchdog-stack.txt`. Точная причина слишком долгого расчёта столкновений и последовательность его отдельного воспроизведения ещё не установлены; не утверждается, что именно изменение `py` в 0.32 внесло этот дефект. Тем не менее, заявлять нормализованное поведение William по двум вызовам tick нельзя: его `WilliamFlightChecks` проверяет лишь предыдущий угол и мягкое вертикальное движение после двух тиков.

После падения клиент отключён сервером; штатное завершение через RCON уже невозможно. До этого были выполнены сохранение мира, возврат игрока и снятие тестовых force-load. Перед дальнейшей игровой приёмкой нужна диагностика движения William в длительном запуске, включая загруженные старые сущности.

### P1. Духовное смещение позволяет перенос без активного духа

`src/main/java/stepsword/mahoutsukai/networking/DoneMentalPacket.java:43–65`.

Проверка возвращает отказ только при одновременном отсутствии сохранённого состояния **и** самого сообщения. Для настоящего сетевого сообщения второе условие всегда ложно. Если принадлежащего игроку духа нет, используются координаты из пакета, после чего вызывается перенос.

**Воспроизведено на нативном сервере:** у игрока нет активного состояния и духа; вызов обработчика с координатами соседней площадки перемещает его на 4 блока. Мана и свиток не требуются. Ограничение дальности не заменяет проверку права на перенос; запрос можно повторять.

Нужно принимать завершение только для активного, принадлежащего игроку духа и текущей сессии, без запасного переноса по произвольным координатам клиента. Затем повторить отрицательный сценарий и нормальные ранний/автоматический выходы.

### P2. Босс бьёт до окончания предупреждения

`src/main/java/stepsword/mahoutsukai/entity/RealityMarbleBossEntity.java:197–215`.

`sonicBurst()` ставит 12 тиков предупреждения и тут же наносит урон. Ожидания между этими действиями нет.

**Воспроизведено:** сразу после начала атаки `attackTicks=12`, но `sonicHits=1`. Счётчик означает вызов попытки урона по игроку; фактическое уменьшение HP fake-player этой пробой не утверждается. Порядок «предупреждение → удар» нарушен независимо от результата hurt.

Текущий тест DeepSeek проверяет положительный таймер и наличие атак по отдельности, поэтому пропускает ошибку порядка. Нужен удар только по завершении телеграфа и проверка возможности выйти из зоны до удара.

### P2. Для награды учитывается даже отвергнутый удар

`src/main/java/stepsword/mahoutsukai/entity/RealityMarbleBossEntity.java:145–152`.

Игрок добавляется в `attackers` до проверки результата `super.hurtServer`. Следовательно, требование «получают те, кто нанёс урон» соблюдается не полностью.

**Воспроизведено:** босс неуязвим, нанесение урона отвергнуто, но `attackerCount=1`. Проверено ошибочное зачисление участника, а не отдельный полный бой до выдачи награды. Зачислять участника нужно после принятого урона с учётом фактического результата.

### P2. Древо раскрывает закрытые рецепты

`src/main/java/stepsword/mahoutsukai/fabric/ResearchProgress.java:65`; клиентский `ResearchScreen.acquisition()`.

Точные ингредиенты добавляются во все соответствующие исследовательские узлы без проверки открытия рецепта. Клиент формирует из них список получения, даже если исследование ещё недоступно. Это обходит прежнее условие «найти хотя бы половину ингредиентов» через другой экран.

**Воспроизведено:** у выживающего игрока с пустым инвентарём и очищенными знаниями найдены **45 закрытых рецептов**, чьи формулы уже доступны через данные исследований. Пример и весь результат сохранены в `audit-0.32/results.json`. Это именно новое отображение закрытых данных; отсутствие серверной тайны у обычных JSON-рецептов само по себе здесь не считается отдельной уязвимостью.

DOOM отдельно проверен: его секретная карточка формулу не раскрывает. Для остальных закрытых узлов нужны общие намёки, а конкретный список материалов — после открытия.

### P2. Новые звуки удвоены по длительности и накладываются

`scripts/generate_doom_audio.py`, функция записи: каждый PCM-сэмпл добавляется два раза через `pcm.extend((value, value))`, но WAV объявлен **одноканальным**. Это повторяет сэмплы во времени, а не создаёт стерео.

Длительность проверена по фактическим Vorbis rate/granule в новых OGG:

| Файл | Задано генератором | Получено |
| --- | ---: | ---: |
| `doom/rumble` | 4,0 с | 8,0 с |
| `doom/impact` | 2,9 с | 5,8 с |
| `mystic/big_explosion` | 1,9 с | 3,8 с |

В `DoomEntity.java:81` rumble запускается каждые 40 тиков, то есть через 2 секунды, с pitch 0,92. Каждый экземпляр длится примерно 8,70 секунды. Предыдущие экземпляры ещё не закончились, когда начинаются следующие. Утверждение «наложения нет» не подтверждается расписанием и самими файлами. Даже исправленные 4 секунды при интервале 2 секунды требуют пересмотра расписания/управления звуком.

Новые звуки отправлены настоящему клиенту нативными sound-пакетами; страх/красота звука не оцениваются как автоматический PASS.

### P2. Видимая модель босса не совпадает с зоной попадания

`entity/ModEntities.java:35`: хитбокс 2,4 × 2,8 блока. `RenderRealityMarbleBoss.java:19`: модель Kodoku увеличена в 3,2 раза. Высота геометрии её самого высокого сегмента — 4/16 блока; после масштаба около 0,8 блока, а не 2,8.

**Подтверждено кодом и реальным кадром:** у земли видна небольшая сегментированная модель, над ней большая пустая зона попадания. Босса можно задевать там, где видимого тела нет. Для визуальной проверки использована команда summon и NoAI на отдельной площадке; это не выдается за завершённый бой в Reality Marble.

Оригинальная модель использована честно с указанием источника, но требование выразительного страшного босса пока нельзя считать закрытым.

### P2. Иконка генератора тумана остаётся сломанной

`assets/mahoutsukai/models/item/fog_projector_gui.json` ссылается на `mahoutsukai:particle/fog3`. В используемом атласе предметов этот спрайт не найден.

**Подтверждено клиентским логом** `Missing textures in model mahoutsukai:item/fog_projector_gui` и розово-чёрной иконкой на кадрах. Сам PNG существует — проверки существования файла недостаточно. Нужна корректная ссылка на спрайт в атласе или включение ресурса в атлас.

Этот черновик иконки существовал ещё до DeepSeek; это дефект итогового кандидата, а не полностью новая ошибка его автора. Иконка обычного наземного Алхимического обмена теперь отображается правильно.

## HUD: причина воспроизведена, панель возвращена

При первом входе тестового Player733 лог показал `hasMagic=false`, `visible=true`, мана `20000/20000`. При этом в `MahouGui.java:127` панель по-прежнему требует `hasMagic()`. Поэтому **одного нового ограничения координат и try/finally недостаточно**: в этом состоянии она всё ещё отсутствует. То же относится к таймерам, которые помещены внутрь этой ветки.

Команда `/showmahou` принудительно выставляет hasMagic и переключает visible. После двух вызовов панель включена; настоящий кадр показывает `20000/20000`, уровень 11. При повторном подключении состояние сохранилось. Это подтверждённое восстановление конкретного тестового игрока существующей командой, а не исправление всех причин исчезновения HUD для каждого игрока.

## Что пока не выполнено полностью

- Красная переделка геометрии большого взрыва посоха: в diff поправлены звук/отдача, но запрошенная новая форма каста не реализована.
- Дополнительный визуал всего оружия: изменений сверх перечисленного нет; «всё стало красивее» не подтверждается.
- Гандр: старые ленты удалены; на реальном первом лице теперь виден непрозрачный чёрный шар с чёрными искрами на стандартных внутренних цветах. Это согласуется с нулевыми вторичными цветами в настройках и непрозрачной внешней сферой. Заявленное светящееся ядро не получилось подтвердить; старые общие печати каста также остались.
- William: карточка каталога по-прежнему даёт общую отсылку к справочнику. Новые переведённые главы и серверная добыча не равны понятному прямому переходу к нужной инструкции.
- Затемнение DOOM реализовано полосами поверх верхней части экрана, а не изменением освещения неба. Эффект виден, но заметна ступенчатость; визуальная приёмка всех направлений камеры/шейдеров не закрыта.
- Полный бой с боссом живого игрока, несколько клиентов, все боевые сочетания, полный набор внешних модов и миграция новой версии на копии исходного мира здесь не проверены. Прежние тесты не заменяют эти сценарии.

## Доказательства и воспроизведение

- Машинный отчёт: [audit-0.32/results.json](audit-0.32/results.json).
- Нативные PNG: папка [audit-0.32](audit-0.32/), 12 кадров.
- Общий свежий лог: `analysis/codex-audit-032-native.log`.
- Отрицательные пробы: `analysis/codex-audit-032-probes.json`, `analysis/codex-audit-032-probes.log`.
- Клиентские логи: `analysis/codex-audit-032-client.log`, `analysis/codex-audit-032-client-final.log`.
- Повтор обычного набора после добавления аудит-проб: `analysis/codex-audit-032-final-regression.log`, `runEconomyChecks build` — успешно, хеш JAR не изменился.
- Дополнительные пробы: `src/selfCheck/java/stepsword/mahoutsukai/Audit032ServerChecks.java`.

Общий набор: `scripts/verify_032.ps1`. Реальный клиент запускался задачей **`runMagicVisual`**, сервер — `runProgressionPreview`, с JDK проекта и `--offline`.

Отдельные отрицательные пробы включаются свойством JVM `-Dmahoutsukai.audit032=true` при запуске test source set через `runEconomyChecks`. Они сохраняют собственный JSON и завершают сервер, не исполняя общий набор. Поэтому завершающая проверка штатного маркера economy ожидаемо отклоняет **этот отдельный запуск**. Это не результат повторного обычного набора: обычный набор без флага прошёл выше. Не удалять проверку маркера ради зелёного статуса.

В первой попытке клиентской проверки был выбран funbook вместо guidebook; утверждение теста корректно прервало клиент. Сценарий повторён с настоящим компендиумом и прошёл. Этот сбой настройки проверки не считается дефектом мода. Сообщения Realms/profile key 401 при локальном dev-входе также не выдаются за дефект мода.

Игровые испытания делались в локальном тестовом мире, для опасных/вызванных сущностей использовалась отдельная площадка. Пробы не трогали пользовательский мир `run/server`. Временный свиток из пустой ячейки убран, тестовые force-load сняты, игрок возвращён к деревне. Панель маны оставлена включённой. Сборка на GitHub не публиковалась.

## Рекомендуемый порядок исправлений

1. Диагностировать watchdog в движении William; закрыть неавторизованный перенос и добавить отрицательные проверки.
2. Убрать раскрытие рецептов, задержать урон босса до конца предупреждения, исправить зачёт участников.
3. Исправить генерацию/расписание звука и соответствие модели босса хитбоксу.
4. Закрыть оставшиеся интерфейсные и визуальные пункты, затем провести настоящий бой и несколько клиентских сессий.
5. Только после этого пересобрать новую версию и обновить чек-лист результатами именно её проверок.
